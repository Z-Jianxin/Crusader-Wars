# Isolated development application

[New-DevelopmentRuntime.ps1](./New-DevelopmentRuntime.ps1) stages selected assets from an existing installation and publishes the current C# application into a **new directory outside both the repository and the installation**. It does not launch the application. Installed save data, battle state, logs, CK3 mod bundles and updater executables are not copied.

```powershell
./Tests/DevelopmentRuntime/New-DevelopmentRuntime.ps1 `
  -AssetRuntime 'C:/installed/crusader-conflicts' `
  -Destination 'C:/test-evidence/development-runtime-01' `
  -DotNet 'C:/dotnet9/dotnet.exe' `
  -AppVersion '1.4.2'
```

The explicit `development-runtime.json` marker disables upstream app/mapper/updater replacement and automatic CK3 mod copying. The normal version file still determines the displayed version; a development suffix and “automatic updates off” label make the mode visible. The marker records source revision, whether uncommitted changes were present, the source asset directory, and the built assembly hash. Without this marker, normal release behavior is unchanged.

For a user-facing standalone folder, add `-SelfContained`. This publishes the Windows x64 .NET runtime alongside the application without trimming or single-file packing; launching the executable then does not depend on a temporary `DOTNET_ROOT` setting. The application sets its working directory to its own folder. Keep the marker and complete asset tree, including RPFM companions and the process-resume helper, and omit the task-only battle controller. Do not carry interrupted battle state, old result/input files or test automation into a fresh user runtime. Confirm native startup with the child process's `DOTNET_ROOT` variables cleared; do not alter the user's global environment.

Use the copied development playset's existing source descriptor. The application does not install or overwrite that CK3 component automatically in development mode. The marker is not a gameplay sandbox: clicking the normal battle workflow can still launch games and import results, so UI tests should use disposable test campaigns.

Startup checks that can open dialogs run from the main window's `Shown` event. When development guards complete synchronously, running those checks inside `Load` can block the first main-window display behind an owned release-note dialog with no taskbar entry. The corrected startup logs `HomePage shown: Visible=..., Handle=..., Bounds=...` before updater/notification checks. Native startup verification on 2026-10-21 confirmed a nonzero main-window handle and the `Crusader Conflicts` title without administrator privileges.

The same native UI check activated the app, dismissed its visible release-note dialog, opened Options, and found the **Preserve CK3 combat stats** checkbox under Unit Scale/Max. Selecting it and closing Options persisted `<Option name="StatFidelityMode">Enabled</Option>` in the isolated runtime's options file. The installed application's options were not touched. For automation, select the Options dialog's own returned window and use its coordinates/accessibility tree; the parent window's clipped view is not the dialog surface.

That initial UI check used runtime02. The current source label is **CK3 combat stats (experimental)**, and enabling it includes anchored knight budgets and strict native levy coverage by default. Runtime04 was staged after the exact combat-result-link fix, with assembly SHA-256 `F0804C6C3AF243B74E36CFF389B405344989E196225F65911B91B26E07D07CEE`. It preserves the original runtime and has no advanced fidelity override file. Its final native UI/gameplay test is separate from the earlier runtime02 checkbox proof.

Runtime06's native UI test enabled the current experimental checkbox and verified persistence; runtime07 preserves that setting and uses strict defaults without an advanced override file.

The staging helper now requires and copies the existing `data/runtime/pssuspend64.exe`. An earlier stage omitted this installed runtime asset and Execute failed before the handoff; the native helper was restored from the original installation and included in the asset audit. Development mode skips OS suspension of CK3: during the first actual trial, suspension made all native Attila activation/input calls time out while screenshots and rendering continued. Resuming CK3 immediately restored input in the same Attila process. CK3 remains paused by the normal exporter. Release suspension behavior is unchanged. Development startup also suppresses frontend movies.

The development marker now also isolates final result publication. The normal importer performs its real casualty, character, combat and war updates, then writes a timestamped `results/<timestamp>/battle_results.ck3` plus a hash manifest under the runtime. It does not replace personal `last_save.ck3`, `save games/battle_results.ck3` or `continue_game.json`. Each result directory also archives the exact native input, handoff and Attila result log with hashes. Successful development Execute and Continue workflows stop instead of automatically clearing evidence for another battle; a new listener requires an explicit Execute. Intermediate input/output files remain available. Load the separate test result explicitly; development mode does not launch CK3 with the personal continue target. Fidelity extraction also uses the exact save selected by the application, rather than discarding that selection and reading a different last-save file.

1. Archive the completed CK3 soak logs first. The application's Execute workflow clears `console_history.txt` and the Attila result log before waiting for a new handoff.
2. Run [Backup-AttilaTrial.ps1](./Backup-AttilaTrial.ps1) once into a new external directory. 3. Open the isolated app, enable **CK3 combat stats (experimental)**, press Execute, then use a new normal Fight handoff in the disposable CK3 campaign. This tests the actual application orchestration rather than only an offline generator.
4. Enter the generated Attila battle and complete deployment. The explicitly installed [test controller](./test-battle-control.lua) issues real attack orders and logs real unit counts/kills. It does not modify stats, health, morale, routing, placement, casualty counts or the winner. Generals are held until their regular fighters are unavailable. The corrected controller was compiled and tested with an empty `_G`, then actually collected all 51 formations (`START|18|33`) in snapshot6 and emitted real telemetry.
5. Wait for a natural Victory/Defeat, dismiss the Attila result, and close the application's post-battle report so result publication can finish. Fidelity rejects absent or contradictory winner records rather than inventing a loss.
6. Run [Capture-ActualTrial.ps1](./Capture-ActualTrial.ps1). It requires one native trial snapshot, one consistent real outcome, complete reports, the dismissal marker and an app-produced result manifest for the same snapshot. It hashes the captured input/output saves against that manifest and checks the captured handoff snapshot. It archives raw evidence without synthesizing result rows. The installed pack is copied and extracted as the authoritative deployed script/XML inventory: the application clears its loose Lua work files after packing. A successful capture still does not claim CK3 reload success.
7. Copy the separate result into a uniquely named disposable CK3 save and verify loading through the native UI. Inspect resulting army/character/combat state and preserved unrelated flags against the captured input.
8. After games no longer use the test files, run [Restore-AttilaTrial.ps1](./Restore-AttilaTrial.ps1). It archives the trial's actual files before restoring every original hash, or removing only named files that did not originally exist. A separate filesystem-only self-test verified restoration; it is not battle evidence.

The test controller is loaded only when both the development marker and `test-battle-control.lua` exist in the runtime. Remove that task-only file for normal player-controlled battles. Normal release packs ignore the hook. The optional [Launch-ActualTrial.ps1](./Launch-ActualTrial.ps1) starts a separately prepared external pack without installing it; it refuses to stop an existing Attila process. That fallback can test the battle but cannot alone prove the application's Execute/install/launch/import sequence.

## Native save-container check

A standard ZIP integrity check and a semantic gamestate comparison are insufficient to validate a CK3 save. Native `SAV0102` files contain a 24-byte ASCII header with an eight-hex-digit **metadata byte length**, then the metadata prefix, then ZIP. Preserve the prefix verbatim, including LF line endings and UTF-8 bytes; do not regenerate it with a platform-default text writer or guess the other header field.

The first corrected offline import passed source/fate invariants but failed a fresh native load because the harness changed 630 LF endings to CRLF while retaining the original embedded length. Its ZIP CRC was valid. The repair restored the exact original 44,894-byte prefix (44,870 metadata bytes) and retained the entire audited ZIP payload and decompressed gamestate unchanged. This is a container-only repair, not another outcome or fate roll. Production and harness paths now preserve native prefix bytes; compression validates the embedded length before publishing. The regression suite covers LF/Unicode roundtrip and refusal of the CRLF-corrupted prefix. A fresh native load remains the decisive final check.

The current source includes this guard and passes 85 model tests and 99 application integration cases. The standalone installation receipt records its assembly hash and whether native startup has actually been observed.

The final self-contained assembly `C648350F08EC4356B82EFECF23C5E9501E84197E3E3260A897A3CEF4ADF17174` reached Ready and closed normally from an unrelated working directory with child `DOTNET_ROOT` and `DOTNET_ROOT_X64` cleared. Its enabled fidelity option and game paths were checked through the native Options window. The installed package contains no automated battle controller. The accepted v4 result also completed a fresh native CK3 load/resave/day check; [the consolidated receipt](../../docs/stat-fidelity-validation.md) distinguishes actual battle evidence, corrected reimport, startup evidence and rejected intermediate saves.

Keep invalid diagnostic wrappers outside CK3's native save catalog. During validation, the invalid v1 test copy was still open while a v2 startup was at “Starting game”; after that process stopped, the exact known test file could be removed and a clean-catalog v2 run started. Do not classify a control load as a payload failure while another known-invalid test save remains in the catalog. Archive the diagnostic externally first, identify it by its recorded hash, and remove only that explicitly named test copy.
