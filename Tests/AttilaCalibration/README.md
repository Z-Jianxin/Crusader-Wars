# Attila engine calibration fixture

This task-only generator creates an isolated historical battle pack and mod-list file in a new scratch directory. It does not launch Attila, write its installed packs, or change its selected mods. It distinguishes generated expectations from native script observations and live unit-card verification.

## Build and prepare

Requires .NET 9, a completed Attila installation, and the installed Crusader Conflicts runtime (for RPFM/schema). Ordinary native suites use boot/data and the selected locale with no overhaul enabled. The separate `active-mounted-auto` probe intentionally uses the complete active stack for actual mapped-unit validation.

```powershell
dotnet restore Tests/AttilaCalibration/AttilaCalibration.csproj --source https://api.nuget.org/v3/index.json
dotnet run --project Tests/AttilaCalibration/AttilaCalibration.csproj --no-restore -- '<CC runtime>' '<Attila root>' '<minimal duel scratch directory>' native-duel 1
dotnet run --project Tests/AttilaCalibration/AttilaCalibration.csproj --no-restore -- '<CC runtime>' '<Attila root>' '<new infantry scratch directory>' native-scenario-infantry 4
dotnet run --project Tests/AttilaCalibration/AttilaCalibration.csproj --no-restore -- '<CC runtime>' '<Attila root>' '<new mounted scratch directory>' native-scenario-mounted 4
dotnet run --project Tests/AttilaCalibration/AttilaCalibration.csproj --no-restore -- '<CC runtime>' '<Attila root>' '<native control scratch directory>' native
```

The generator selects a vanilla melee unit, verifies dependencies, builds private variants with the production backend, compiles both Lua scripts without executing them, packs the fixture, and verifies every generated TSV value after binary roundtrip. It records the source unit, source packs, generated stats, case keys and pair definitions in `manifest.json`.

The infantry suite has generated baseline versus baseline, native unit versus generated baseline, double damage versus baseline, and double infantry HP versus baseline. Four replicates produce sixteen independent lanes. The native comparison checks that creating a neutral variant has not itself changed combat. Odd/even replicates switch the treated side. The mounted suite has generated baseline, native unit versus generated baseline, doubled man entity HP, doubled mount entity HP, and both entity HP fields doubled, producing twenty lanes. The original land bonus HP is preserved in these experimental cases to isolate each entity's contribution. Generation checks that the neutral clone preserves every man-entity stat, land bonus HP, and mount reference/count. Production now scales all three HP components proportionally, based on the completed observations below. Four replicates per case are pilot observations; repeat launches for a useful sample.

Current preserved-scenario pairs use the selected native unit's soldier count (160 for the selected infantry, 80 for cavalry), at zero experience with matched orders and fearless morale. They retain the native Visigoth/Roman army factions and original generals. Remote invincible generals keep the battle alive while pairs finish; unused original unit slots are disabled through native Lua methods. Fire-at-will is disabled and candidates exclude missile weapons. Pairs have spaced lanes and script controllers retain control after their opponent dies. Terrain is the fixed native Adrianople historical map, not a guaranteed flat map; repeated mirrored trials help identify positional/faction bias but cannot remove every battlefield effect. The older rewritten-army `infantry`/`mounted` modes used sixty-man units and remain for reproducing the documented pre-Lua crash, not as the recommended test path.

## Launch contract

The operator/root agent owns all game launches. Ensure Attila is closed before changing fixture packs. Use the generated `used_mods_cc_calibration.txt` alone, with Attila's working directory set to its game root. The file has an absolute `add_working_directory` pointing to its scratch pack. If Attila does not accept an absolute mod-list command-line path, copy this task-specific text file to the game root and pass its filename; never replace `used_mods_cc.txt`.

The task startup script also requests `show_frontend_movies false;`. This option and its help text, "Use to disable intro movies", are present together in the installed `Empire.Retail.dll`. The root operator verified that this startup-script setting reaches the main menu quickly without the long introductory movie. This keeps the setting in the task script without changing global preferences or replacing movie assets. Earlier prepared fixtures have a separate `used_mods_cc_calibration_no_intro.txt` candidate with this added line. Wait for the previous Attila process to fully exit before launching another fixture, or its single-instance mutex can reject the launch.

After the normal frontend finishes loading, use **Historical Battles > Adrianople**. The fixture reuses that native registration and its terrain/environment, overriding its battle XML and pointing it at the calibration script. The frontend is the original native script with event logging; there is no startup timer. The battle script uses `bm:setup_battle`, matching the `prevent_deployment=true` path in Attila's `generated_battle` library. Note that `bm:end_deployment()` itself only releases input focus: it is not an engine start command.

Suffix `-auto` (for example `native-duel-auto` or `native-scenario-infantry-auto`) changes only the frontend launch path. After `UICreated`, it schedules a five-second native `tm:callback`, checks that the native `m_root` is assigned, and requests `FrontEnd.start_historic_battle("Adrianople")`. Missing UI-root readiness is retried at one-second intervals with a thirty-attempt limit. Scheduling, readiness and launch return/error are logged. It does not launch during module import. The prepared `native-duel-auto-01` was compared with manual native-duel-02: its battle XML and database match exactly, and the battle controller differs only in log path. The root operator subsequently verified automatic menu-to-battle loading, and the log confirms successful launch, Deployed and real combat samples. This does not bypass the battle's Start Battle button.

The root operator owns the menu interactions. If the engine still waits on deployment, `battle.csv` records the `Deployment` phase; that is a harness failure to investigate, not a completed trial. Do not fabricate success from a generated pack. Scripts remain unverified in the actual engine until a real run emits `START`, paired samples and `COMPLETE`.

The `native` control suite contains only two native Lua files with added logging. It has zero generated stats, DB rows, XML, terrain, or gameplay changes, and also launches through **Historical Battles > Adrianople**. Its `native-control.log` records frontend/UI events and entry into the native Adrianople battle script. Use this to distinguish installation/frontend failures from calibration-fixture failures. It does not produce combat-analysis CSV and should not be passed to the analyzer.

### Prior failed bootstrap

The earlier `infantry-04` attempted `FrontEnd.start_historic_battle("tut_tutorial_battle")` from a five-second native frontend timer. In the actual run the timer became due only after the long introductory cinematic. The process died before returning from the launch call or loading the battle script. Windows recorded an `Empire.Retail.dll` access violation (`c0000005`, offset `00132b60`); the CA stack contained only unknown frames. These observations do not establish whether early launch timing, custom battle registration/XML, or another native issue caused the crash. The current control/menu workflow removes these simultaneous assumptions. `infantry-05` was generated with that same old bootstrap and should not be used for the revised path.

The native-control-01 battle subsequently rendered successfully through the ordinary menu, including terrain, infantry/cavalry and unit-card values. Its initially black screen was the native fade/cutscene interval. However, infantry-06 still crashed at the same native offset before entering the calibration script, despite using the proven menu/map path. Generated database data and rewritten battle XML therefore require separate isolation; native control success does not validate generated stat variants.

### Minimal native-unit isolation

Use suite `smoke-unused` to add one generated damage-2/HP-1 Germanic Spearmen definition while leaving the native Adrianople XML wholly unchanged. Use `smoke-single` to change only `Vgt_02`'s `unit_type` to that generated key; script name, faction, position, experience, general status and every other native unit remain untouched. Both retain native battle gameplay/script and add logging only. `smoke-unused-compact` and `smoke-single-compact` differ by changing the generated `main_units.unique_index` from the production hash-derived value to the first unused positive 32-bit index, checking all active native IDs for collisions. These compact variants are experimental until engine verification. Native records themselves include large 64-bit IDs, so index magnitude alone is weak evidence of the crash cause; `max(native index) + 1` does not produce a compact index. Their manifests record both indices, and all generated table fields are checked after binary roundtrip. Inspect `native-smoke.log` and the Vgt_02 unit card; these smoke fixtures do not generate the paired-combat CSV.

The root operator verified that `native-db-01` reaches rendered battle and logs native setup plus Deployment/Deployed with its generated profile unused. That establishes that loading the profile database alone does not reproduce the paired-fixture crash. It does not yet establish that the generated unit can spawn or its altered damage works. New smoke fixtures preserve the original XML encoding/BOM as well as its content: native Adrianople XML is UTF-16LE. Earlier smoke-single fixtures used UTF-8; production Crusader Conflicts also emits UTF-8 XML, so encoding is an isolation variable rather than a proven engine requirement.

**Verified engine observation, 2026-10-21:** `native-single-huge-01` loaded and rendered the actual generated Germanic Spearmen in the native Adrianople battle. Its log recorded `Vgt_02 type=cc_sf_fdc73e62e62e62dac028e17f men=160`, followed by Deployment and Deployed. The root operator inspected the live unit card: melee damage **64**, health **97**, melee attack 32, charge 29, defence 42, armour 53, morale 41, speed 32. Native source weapon `att_spear_heavy` has damage 24 + AP 8 = **32**; the generated weapon has 48 + 16 = **64**. Source and generated health components both remain entity 90 + land bonus 7 = **97**. Thus this run verifies actual generated-unit spawning and doubled displayed weapon damage with preserved neutral HP, beyond pack-input/roundtrip checks. It also demonstrates that the tested large index and UTF-8 XML can load. It does **not** yet validate non-neutral HP, mounted semantics, paired combat outcomes, CK3 export/integration, or exact cross-game combat equivalence.

Suite `infantry-native-generals` keeps the infantry trial data unchanged but clones the native Adrianople `Rom_01` cavalry general for both remote sentinels. It preserves that unit's general data, experience, width and default soldier count; only script name, remote position and orientation change. This isolates the old fixture's use of ordinary infantry as a general. For the prepared `infantry-native-generals-01`, a separate comparison confirmed that its generated combat database and remaining XML match infantry-06; engine validity still requires a run.

Both `infantry-native-generals-01` and its `paired-native-roster-01` control subsequently crashed before Lua at the same native offset. The latter used only native trial units with its generated DB unused, isolating the problem to the rewritten battle XML/scenario. Current mode `native-duel` instead keeps the original Adrianople XML, all 51 native unit slots, metadata, factions, real generals, deployment regions, battle description and map. In the prepared `native-duel-01`, a full XML comparison found only two attribute changes: player `Vgt_02` experience 2 to 0, and enemy `Rom_02` type to native Germanic Spearmen. A custom replacement of the original `an_start.lua` disables unused slots and positions the selected units through native controller methods after loading. `native-scenario-infantry` can use the same scaffold for the complete infantry treatments once the minimal duel is proven. These scenarios retain native soldier counts (recorded as `expectedMen`), rather than assuming sixty. A baseline-only/native-roster control is explicitly excluded from stat-treatment evidence by the analyzer.

`native-duel-01` subsequently loaded, entered Deployed and sampled two 160-man units, but recorded no casualties through the initial observation window. `native-duel-02` keeps the exact same XML/database and changes only controller sequencing: active units are never temporarily disabled; inactive controllers are retained; teleporting waits until after Deployed; attacks follow one second later. Position diagnostics record both actual and ordered X/Z before/after teleport, at attack orders, and every five seconds. This distinguishes travel/placement/order failures from a pre-Lua crash. A completed timeout with no observed casualties is not counted as valid casualty evidence, even when every expected unit loaded.

`native-duel-02` completed its observation at controller counter 300 with 93 versus 65 survivors and 95 versus 67 enemy kills, with no script errors or cross-pair casualty discrepancy. This proves engagement and telemetry on the native scaffold; its asymmetric baseline motivates mirrored trials and is not a treatment result. The full suites restore HUD, ordinary camera mode and conflict-clock updates using the same calls as native `cutscene:release()`, and frame the first pair after teleporting settles. `UI_RESTORE` and `CAMERA` records report whether those optional presentation actions succeeded.

Mode `smoke-counts` preserves the native historical scenario and requests `Vgt_02=20` and `Vgt_04=500` soldiers against a generated unit whose nominal DB count remains 160. It logs both actual counts before deployment. This is a representation-count probe, not a balanced combat trial; do not infer body-budget support from its requested XML values without checking engine output.

`smoke-counts-auto` uses the shared, verified frontend auto-launch helper. The prepared `native-counts-auto-01` has explicit requested/nominal counts in its manifest and actual-count logging for both units. No installed pack or startup list is changed by preparation.

**Completed infantry treatment pilot:** `native-scenario-infantry-auto-01` reached its cutoff at controller counter 300 with no script errors, initial-placement failures, out-of-bounds units, lane departures or casualty contamination. All four doubled-damage trials had positive survivor margins (89, 108, 126, 147; median 117); three eliminated the control, while the fourth left one control soldier at the cutoff. All four doubled-HP trials also led (40, 42, 85, 92; median 63.5). Two baseline lanes and one native-versus-clone lane had no observed casualties and were excluded. Remaining controls varied substantially, so this is directional engine validation, not exact DPS or CK3 outcome equivalence. The root operator separately inspected an HP-2 unit card showing health 194, damage 32 and zero XP. Its raw logs and `analysis.json` are archived with the fixture.

The newer `native-scenario-mounted-auto-02` forces active participants visible through the shipped `script_unit:set_always_visible(true)` method. This removes concealment as one possible reason for idle control lanes; it does not claim to have established the cause of the earlier idle lanes.

**Completed mounted treatment pilot:** all twenty lanes reached the observation cutoff at controller counter 300 with valid engagement and no script errors, placement failures, bounds/lane departures or casualty contamination. The root inspected zero-XP Catafractarii cards during combat: baseline **232 = 90 man + 17 bonus + 125 mount**, rider-only **322 = 180 + 17 + 125**, mount-only **357 = 90 + 17 + 250**, and both-entity **447 = 180 + 17 + 250**. All retained melee damage 10. Rider treatment survivor margins were 28/53/54/30 (median 41.5), mount treatment 65/19/55/28 (median 41.5), and both treatment 71/62/69/56 (median 65.5); all four both-treatment controls were destroyed. Baseline margins 20/-35/24/-4 and native-versus-clone margins 26/-36/17/46 show material variance. These establish the composite card formula and directional mounted durability response, not exact kill-rate scaling. Raw logs and analysis are archived with the fixture.

**Count override observation:** `native-counts-auto-01` logged actual native `Vgt_02 men=20` and `Vgt_04 men=500` on the same generated type with nominal DB count 160. This supports the tested smaller/larger formation requests independently of quality profiles. It is not a casualty-budget calibration.

The production backend now preserves rounded mounted and dismounted totals while scaling man/bonus/mount proportionally, using private mount records/entities. It rejects unsupported special entities and preserves identity-factor components exactly. Dismounted combat still needs its own measurements. See the [backend contract](../../docs/STAT_FIDELITY_BACKEND.md).

### Active-stack production card probe

Mode `active-mounted-auto` takes two additional arguments after the mode: an existing completed cache root and a three-profile JSON file (neutral Catafractarii, Catafractarii with HP multiplier 2, and the actual anchored knight profile). It uses production `Prepare`/`Generate`, the complete active mod stack, original native Adrianople scripts/XML and three minimal unit type/count/XP changes. The generated startup file excludes the installed prior Crusader Conflicts battle pack and includes the eight mapped asset mods. All generated fields undergo binary roundtrip; the manifest separates expected cards from actual native count logs.

Prepared `active-mounted-auto-02` targets **Vgt_02: 120 men, damage 10, HP 210**, **Vgt_03: 120 men, damage 10, HP 420**, and **Vgt_04: 43 men, damage 247, HP 151**. All are XP0. Active 919 changes the Catafractarii source to man100 + bonus0 + mount110, so the correct active-stack HP2 value is 420, not vanilla 464. The knight profile comes from the real framed station03 export; its source composite HP is 150, and emitted 43×151 HP / 43×247 weapon-damage budgets reflect integer rounding. The earlier `active-mounted-auto-01` retained native XP and is superseded.

**Verified active-stack observation, 2026-10-21:** the root operator loaded and rendered `active-mounted-auto-02` with all eight actual asset mods. Native logging confirmed the generated subject types/counts. The live mapped knight card showed **43/43 soldiers, XP0, melee damage 247 and armour-piercing damage 99**, with no missile weapon. The 99 AP damage is included in the displayed total 247; it is not an additional 99. This verifies the real mapped knight's model/formation and emitted damage in the overhaul. Its UI replaces the health row with other stats, so **210/420/151 HP were not visually verified in this full-stack run**. Those remain production query/emission and binary-roundtrip expectations, supported separately by the vanilla mounted component-card/combat experiments. No extra UI override was added to reveal health, and this native gameplay probe is not a controlled casualty or CK3 outcome-equivalence trial.

Timing terminology: the calibration controller increments its counter by one per requested 1,000-ms callback; the actual-battle controller increments by ten per requested 10,000-ms callback. These are **controller seconds/ticks**, not a verified simulation clock. The shipped `lib_battlemanager.lua` delegates callbacks to `lib_timer_manager.lua`, which uses native `battle:register_singleshot_timer`/`register_repeating_timer` and maintains `timestamp_tick` from a repeating timer. Those Lua wrappers do not document how native timers respond to fast-forward or pauses. No direct simulation-clock API was measured. Keep raw counters, wall timestamps and observed speed settings separate; do not infer DPS or accelerated simulation duration from the counter alone.

Logs go to absolute task-owned paths beside the fixture:

- `frontend.log`: native historical menu events.
- `battle.csv`: script load, phase changes, unit types, initial counts, one-second samples, pair completions, errors and completion.
- `manifest.json`: immutable fixture definitions and expected records.

The operator may close Attila after `COMPLETE` appears. The script leaves remaining units untouched after recording completion, avoiding extra scripted casualties. A run times out at controller counter 300. Record wall-clock start/end and the native speed setting separately; fast-forward does not establish how callback timing scales with the simulation clock. Repeated launches append a distinct timestamp run ID. Do not run the same fixture concurrently, because simultaneous writers would share its log.

```powershell
python Tests/AttilaCalibration/analyze.py '<scratch directory>'
```

The analyzer reports mirrored treated/control survivor margins, observation durations, incomplete runs and possible cross-lane contamination. A run contributes valid trials only after START, COMPLETE, all expected lanes, correct actual unit keys, and initial/final samples are present without script errors. Initial units must contain the manifest's `expectedMen` (legacy fallback sixty) with zero kills; otherwise unit-size scaling or premature combat invalidates that fixture. Kills must match the paired opponent's losses, including the final sample after a pair finishes. Native-scenario telemetry also checks starting centroids within twenty metres of requested points, live centroids inside the 1924-metre playable square, and no departure more than forty metres from the assigned lane. Intended infantry lanes span z=-600…600 and mounted lanes z=-760…760, inside the map's ±962-metre boundary. Zero-casualty trials are excluded. `median_seconds` retains its historical field name but measures the controller counter, including timeouts. It is neither verified simulation time nor an uncensored estimate of time to destroy a unit. A positive treatment margin is useful evidence, not proof of an exact multiplier or deterministic battle result. Run `python -m unittest discover -s Tests/AttilaCalibration -p test_analyze.py` to verify these evidence checks (eight tests currently pass).
