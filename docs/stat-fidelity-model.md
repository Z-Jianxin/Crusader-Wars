# CK3 stat fidelity model and current limits

The experimental **CK3 combat stats** option replaces selected XP approximations with generated Attila database profiles, including native MAA and owner-levy bonuses, commander advantage, and anchored knight prowess/efficiency budgets by default. Its tooltip and coverage report state the supported scope. It does not promise identical battle outcomes or identical strength between different unit types. Tactical deployment, armour interaction, hit probability, formation, morale, fatigue, range and pathfinding remain Attila mechanics.

The [accepted actual-battle and final-build receipt](./stat-fidelity-validation.md) records the successful corrected native return and final standalone startup, with a separate [machine-readable receipt](./stat-fidelity-validation.json).

## Evidence and conversion

[HandoffLog.cs](../CrusaderWars/stat_fidelity/HandoffLog.cs) first selects the latest explicitly begun `CCHANDOFF|v1|BEGIN` / `CCHANDOFF|v1|END` group. Both the legacy battle context and native stat export must be inside it. A missing current player/owner/commander identity, date, location, terrain, winter or special-building field fails; no earlier handoff supplies that field. Duplicate required fields and an incomplete latest group also fail. The current parser resets persistent terrain/crossing and realm-display state before using a new group. Enabled fidelity requires framing even when development partial-stat coverage is allowed.

[StatExport.cs](../CrusaderWars/stat_fidelity/StatExport.cs) accepts a bounded `CCSTAT|v1` stream. Each snapshot requires matching `BEGIN` and `END` identifiers. Only the latest frame is considered; an incomplete new frame cannot revive an old battle. Limits are 32 MiB of log text, 2,048 characters per record and 20,000 records. Numeric values use invariant decimal syntax. Unknown values, unsupported versions, duplicate identities and invalid numbers generate diagnostics instead of inferred values.

Record layouts:

```text
CCSTAT|v1|BEGIN|snapshot-serial
CCSTAT|v1|REGIMENT|side|armyId|regimentId|ownerId|type|stationProvinceId|damage|toughness|pursuit|screen|baseDamage|baseToughness
CCSTAT|v1|LEVY|side|ownerId|damage|toughness|baseDamage|baseToughness
CCSTAT|v1|COMMANDER|side|characterId|advantage|damagePerAdvantage
CCSTAT|v1|KNIGHT|side|characterId|prowess|effectivenessMultiplier|damagePerProwess|toughnessPerProwess
CCSTAT|v1|END|snapshot-serial
```

`side` is explicitly `attacker` or `defender`. `source` in the type field means resolve the real type from the exact save regiment identity; localized display names are never identifiers. `none` is permitted for an unavailable army ID when side, regiment ID and owner ID still match the participating save chunk. A verified commanderless side uses character ID `none` and advantage zero. `unknown` is rejected. Exported records from unraised or otherwise nonparticipating regiments are not applied to units.

The additive `LEVY` record is an owner profile, matched by the exact saved army owner and combat side. It applies effective/base damage and toughness ratios to that owner's mapped levy units, with commander damage applied once. Missing owners, including an entirely absent levy export, fail default strict coverage; a garrison is not assumed to share the levy profile. Historical exports need an explicit `RequireCompleteLevyCoverage:false` opt-out to retain mapped-base levies. A pure-levy army can supply a knight anchor only when its own native owner profile and a supported foot-melee template are available; another army's stats or a guessed 10/10 baseline are never substituted.

[SnapshotEvidence.cs](../CrusaderWars/stat_fidelity/SnapshotEvidence.cs) then binds `snapshot-N` to the selected player's saved `ccstat_snapshot_serial` and requires `ccstat_combat` to match the combat selected by the existing save reader. Parsing is bounded to a 2 MiB character block and ignores braces in quoted text. The numeric save encoding was verified in the current engine: an explicitly set value of 1 produces `type=value identity=100000`. Native CK3 1.20.1.2 combat scopes serialize as `type=com`; for combat ID 0 the `identity` field is omitted. This was verified against the actual combat02 snapshot-2 and snapshot-3 save/log pairs. Omission is accepted as zero only for the native combat type; malformed explicit identities remain errors. Profiles and source-preserving grouping are inactive until binding succeeds. Missing or stale evidence is rejected before conversion in the default strict mode.

For a matched regiment:

```text
damage multiplier = effective CK3 damage / base CK3 damage
HP multiplier     = effective CK3 toughness / base CK3 toughness
```

The mapped Attila template supplies the reference type. This preserves upgrades relative to that template. It does not by itself establish absolute balance across different CK3 types or different Attila unit mappers. The exported owner/station/title getter's coverage of combat-only counters, terrain and army/accolade bonuses must be established separately; a field named effective is not proof of complete combat coverage.

For commander-derived advantage, both sides and the active rules coefficient must be present and agree:

```text
side damage multiplier = 1 + max(0, own advantage - opposing advantage) * active coefficient
```

This multiplier is applied once to that side's represented troops, including the general's bodyguard. It uses the character's commander advantage, not the displayed whole-combat advantage: the real fixture proved martial, leading one's own troops, Never Back Down and Chivalry Focus contributions. Conditional terrain/faith/supply effects and combat rolls are not presumed included. Legacy commander/trait XP and the extra leading-own-troops XP are removed on these profiles, as are Martial-derived defensive deployables and the general's legacy accolade abilities. The general has zero XP and a constant one-star baseline. Its current default target is a 30-body detachment funded from actual same-army troops, using the donor's template and effective quality; casualties return to that donor's native population. A commander contributes a personal prowess/efficiency budget only when its native knight record has current strength and positive selected-combat participation. That character is excluded from pooled knights. An unfunded, non-knight general retains only the two-body engine minimum. Separate unverified legacy conditions remain XP. No extra Martial coefficient is added on top of exported advantage. The coefficient is supplied by the active game definition, not a historical hardcoded CK3 rule.

Pursuit and screen are retained as source evidence but currently do not modify Attila movement or chase damage. Siege-progress stats are not treated as field weapon damage. Fidelity artillery uses validated active-pack crew/engine metadata, while explicit zero-participation field equipment remains in reserve. Levies use the owner schema when exported. Independent native garrison combat stats are unverified: fidelity generation rejects garrison profiles rather than substituting an army-owner or levy profile.

Ordinary troops now use a separate [native population ledger](./active-population-validation.md). The selected combat's explicit `current` supplies fighting strength; its explicit `soft_casualties` stays out of the Attila roster. Native source/cache stock is validated against the rounded sum of those two values. The difference between integer stock and that sum is a rounding residual, not another wounded population. Source/chunk identities, original stock, capacity and historical starting values remain distinct.

Attila losses affect only the deployed active population, including active bodies lent to a commander's guard. The return projection aggregates raw survivors before normalizing active strength down to five decimal places once per native army-regiment. Returned integer stock is jointly apportioned from `ceil(active remaining + original soft casualties)` within original source bounds; final-phase allocations cannot exceed main-phase allocations. Original wounded values are preserved for CK3 completion. No recovery percentage or new pursuit formula is inferred. Native recovery and retreat behavior after loading this new path still require user gameplay confirmation.

## Source identities and battle results

Fidelity selects the exact combat from the selected player's serial-matched saved combat scope before reading its armies; it does not search for an owner substituted as commander or fall through to the last combat. It follows that combat's saved `combat_results` link and checks the result's province, so an older battle in the same province cannot receive the new results. A commanderless side has an untracked generic Total War general. It has no CK3 character identity, produces no character-death report, and is excluded from character lookup/fate processing. Its loss cannot kill, wound or capture the army owner. Main-side native/save commander contradictions fail explicitly. Disabled mode retains the legacy behavior.

[Unit](../CrusaderWars/data/save_file/Armies_Objects.cs) retains army, army-regiment, regiment, chunk and owner IDs separately from the mapped Attila key. Units with different source chunks cannot be combined merely because they share a type and culture. Every Attila split copies the source identity. Generated database keys are used for battle XML only; original keys still identify templates and display names.

[CasualtyProcessor](../CrusaderWars/data/battle_results/CasualtyProcessor.cs) adds raw reports for every split belonging to an exact source chunk. It never borrows the first report for another same-type regiment. Missing or ambiguous split reports abort the save-update path. [MAA source budgets](../CrusaderWars/stat_fidelity/MaaSourceCohorts.cs) and [levy cohort budgets](../CrusaderWars/stat_fidelity/LevyCohorts.cs) validate original stocks and planned active bodies. The [native population ledger](../CrusaderWars/stat_fidelity/NativePopulationLedger.cs) now owns active/wounded return arithmetic: exact raw ratios are aggregated, active strength is normalized once per native army-regiment, and returned stocks are jointly apportioned across its original chunks. Guard detachments participate in their donor's projection; personal knight bodies do not become extra ordinary troops. Native pursuit losses use the difference between these main/final stock projections, while credited kills remain raw Attila values. Legacy stock projection remains for the older path without native population evidence.

Fidelity preserves native levy culture IDs instead of redistributing small cultures or merging different cultures merely because they share an Attila faction. Positive cohorts with no effective mapping, no positive-weight pool, or no represented bodies fail before pack publication. Missing source culture may use the already-read army owner's culture for appearance without changing source identity or strength; absent both, conversion fails instead of moving soldiers into another unit. [Scale tests](../Tests/StatFidelity.Integration.Tests/LevyCohortScalingTests.cs) cover 25%, 50%, 75%, and 100%, including 101 native soldiers represented by 76 bodies at 75% and equal results for split/unsplit MAA. These are offline corrections; the earlier native roundtrip receipts do not claim a new game test of this later code.

A positive active cohort rounded to zero by battle scaling cannot be represented faithfully and produces an explicit error asking for a larger battle scale. An all-soft cohort has no fighting bodies and does not spawn. A native knight with positive fractional participation retains one character identity; personal retinue bodies represent its combat budget, not extra native people or literal character health. Disabled mode retains legacy grouping and behavior.

## Knight calibration

The native saved knight roster and validated CCSTAT records determine membership and prowess in enabled fidelity mode. Character names and cultures are read from the save. A real Chinese handoff produced zero matches in the legacy localized-tooltip parser while the native save/export both contained five knights; that parser no longer decides whether those characters exist. Missing native knight evidence fails the default strict path. Legacy efficiency expects an additive percentage, so a native total multiplier of 2.35 becomes +135%, preventing a second base-efficiency bonus.

Direct anchored knight conversion is **included by default** when the fidelity option is enabled. Advanced configuration can explicitly set `EnableKnightCalibration:false` to retain the older representation, which the coverage report identifies. Positive fractional native participation now weights each character's nominal damage/toughness contribution while retaining one character identity; zero participation supplies no personal fighting budget. The default is nominal independent damage/health budget matching; empirical combat response remains experimental.

`KnightBudgetMode: "Anchored"` now budgets native damage and toughness independently against the largest verified same-army foot-melee MAA source using the actual active Attila database, with a verified owner-levy fallback if no MAA anchor is available. It chooses the minimum retinue body count satisfying configured bounds, reports integer rounding, applies side commander advantage to damage once, and applies battle scale to both budgets. It fails if no supported anchor exists or the representation's HP path is unverified. There is no guessed levy 10/10 fallback and no silent foot-template replacement. See [calculation, measured limitations and required tests](./knight-budget-calibration.md).

The owner-levy fallback uses the army's effective mapped levy pool, including its replacement/filter rules, rather than requiring levy units to have been emitted already. A positive-weight melee-primary infantry template with verified foot HP can provide the nominal reference, including infantry with precursor weapons. Coverage identifies the reference as a levy-pool calibration choice; it is not a claim that the randomly selected small-levy formation deployed that template. The reference remains deterministic before and after composition, without drawing additional randomness, constructing extra units, or borrowing another army's stats.

An automatically mapped conventional missile-equipped knight template can use a supported melee-only representation from the exact winning faction block and effective author rank, preserving mounted/foot form. Eligible knight entries are preferred; general entries are a secondary retinue representation pool and do not create another commander or budget. Original/replacement keys and mapper-role provenance are logged. Explicit manual/autofix/template overrides and title/default-faction mappings are not silently replaced. Naval, special, zero-melee and unverified-HP originals remain unsupported.

This correction reproduced a captured mercenary-army failure, then completed offline battle and active-database generation from the same input. All 159 integration tests passed. An additional, explicitly synthetic full-army casualty check stopped on mangonel survivor accounting; that separate check remains unresolved. No actual battle result was imported and no native UI/game retry was performed for this patch. This is generation validation, not a new full battle-return certification.

The old four-body/prowess-ten reference remains only as explicit `KnightBudgetMode: "TemplateRelative"` test mode. Its nominal knight/huscarl offense ratio was approximately 15.7 times too low in the actual snapshot-6 mapper; relative prowess improvements alone did not solve absolute budgets.

With complete evidence and calibration enabled, prowess XP is zero, prominent knights remain in their character pool instead of also increasing MAA XP, and legacy accolade abilities are not stacked onto direct-stat formations. A commander also listed as a fighting knight receives one budget through its general formation, without a duplicate character/fate roll. Retinues can split into multiple formations; casualties and kills aggregate before one character-pool pass. A zero-strength roster produces no fighting formation. Ordinary commanders still use a minimal engine-required guard. Body allocations are abstractions, not additional CK3 knights, and individual battlefield kills are not directly measured.

## Configuration and reporting

[StatFidelitySession.cs](../CrusaderWars/stat_fidelity/StatFidelitySession.cs) reads optional `settings/StatFidelity.json`:

```json
{
  "MinimumMultiplier": 0.01,
  "MaximumMultiplier": 1000,
  "CommanderBodyguardSoldiers": 2,
  "RequireCompleteRegimentCoverage": true,
  "RequireCompleteLevyCoverage": true,
  "RequireCompleteExport": true,
  "EnableKnightCalibration": true,
  "KnightBudgetMode": "Anchored",
  "KnightTemplateOverride": "",
  "KnightMaximumMultiplier": 25,
  "KnightMinimumBodies": 2,
  "KnightMaximumBodies": 10000,
  "KnightMaximumFormationSize": 0,
  "KnightDamageResponseFactor": 1,
  "KnightToughnessResponseFactor": 1,
  "KnightCalibrationEvidence": "nominal-stat anchor only; combat response not fitted"
}
```

Out-of-bounds values fail explicitly. There is no silent clamp, and a zero value is not raised to a positive floor. The Attila backend separately rejects unsupported table references, invalid field ranges or integer overflow. A failed generation cannot install XML pointing to missing generated profiles. Profile registrations reset for each regeneration attempt, including manual unit replacements.

The generated `data/stat_fidelity_coverage.json` records accepted evidence, per-profile scope, configured limits and diagnostics. Disabled mode preserves the legacy path. When enabled, the default `RequireCompleteExport` rejects absent, incomplete or invalid snapshots and requires both sides' commander evidence; the error explains how to disable the option for legacy conversion. Enabled knight calibration also requires the complete original roster before any redistribution. A completed snapshot missing a participating non-siege MAA record fails conversion by default, preventing an asymmetrically upgraded battle. Failures happen before installing the new pack or updating CK3 saves, and write the coverage report.

Development configuration may explicitly set the completeness settings false. Applicable unmatched data then retains legacy behavior with diagnostics. Missing levy owners require disabling `RequireCompleteLevyCoverage` (and, for partial owner rows, regiment coverage) explicitly. Such a configuration is partial coverage and is not a claim of a lossless full-combat translation.

## Actual battle and corrected native import

On 2026-10-21 the real snapshot7 handoff completed the application's normal conversion/install/launch flow. Native Continue Battle then regenerated the same bound input after test-controller repairs. Attila ended naturally in Defeat at controller counter 1,380; this callback counter is not a calibrated simulation clock. Both survivor phases and both kill phases contain all 51 exact deployed formations: 8,002 to 2,975 attackers and 4,892 to 263 defenders. No stats, health, morale, casualties or winner were forced by the task-only controller.

The first imported save was rejected by independent native inspection. Inherited writer bugs killed all fallen knights regardless of their already-resolved wounds/capture outcomes, collapsed multi-chunk levy sources, dropped compact-source metadata, retained stale knight/current-combat caches, and could overfill a one-person levy chunk through rounding. Those outputs remain diagnostic evidence; they are not the corrected campaign result.

The corrected importer binds every raw formation name and body count before any mutation, including levy splits, tracked/untracked generals, knights and siege representations. Missing, duplicate, malformed, unknown, increasing or out-of-bounds survivor records fail. The actual AAR passed, and 20 targeted mutations of its real rows were rejected. Empty-culture generic-general rows from the original battle remain exact identities during explicit offline recovery; repaired future generation uses the saved owner's actual culture.

Source updates now preserve every existing chunk/index/root maximum and unrelated metadata. A bounded largest-remainder survivor allocator conserves each levy aggregate without increasing a source above its original current count. Character injury/capture/death is resolved once and reused during serialization. Captured/slain knight caches lose current strength; uncaptured wounded knights remain available. Current combat totals use native CK3 regiments, while original initial/deployed counters remain unchanged.

Combat-local updates match complete numeric regiment IDs, so an update for regiment 6 cannot touch regiment 65. Missing bound combat data or either native side aborts fidelity import before a partial combat file is published. The [result writeback tests](../Tests/StatFidelity.Integration.Tests/ResultWritebackTests.cs) cover those negative cases and preserve the legacy disabled-mode fallbacks.

Native report statistics are grouped by side and exact MAA type, levy pool, or knight ID, matching CK3's own result schema. All allied source regiments contribute once to these groups. Loss totals use the preserved native initial count and returned CK3 survivors. Kill credits retain the raw Attila AAR values rather than being forced to equal losses; routing losses and abstract retinues prevent that equality. Unfunded engine-only guard credits have no native troop group and are explicitly excluded. Funded guard credits return to their donor; a verified personal knight contribution receives a deterministic modeled share of that formation's credits. A pooled knight unit also cannot reveal individual character kills, so those shares are deterministic modeled allocations weighted by the established knight strengths. The result's archived statistics receipt records the conventions used for that battle. Pursuit-phase cause attribution is not independently calibrated; the tested actual battle had identical final phases and zero additional pursuit deltas.

The importer uses its survivor target to calculate losses and side totals but preserves this pending zero. Nonzero prefilled accumulators are rejected. Native completion preserved all supplied main/pursuit kill and loss fields, initial counts and damage-last-tick fields exactly; it populated final counts and the normal winner/date/war-score/reward summaries.
